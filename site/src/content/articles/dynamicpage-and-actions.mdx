## What happens between a config file and a click

The first article introduced the idea: a page is data, and one engine does the work. This one goes inside the engine: what `DynamicPage` does when a test calls `goto` or `executeSection`, how an action name like `'fill'` becomes code that runs, and what the wrappers around Playwright add, and what they deliberately don't.

The last part is a case study from production: an autocomplete action that reported success when nothing had been selected. It's a small bug, but it teaches a rule that applies to any actions layer: an assertion that checks something your own action just did proves nothing.

As before, all the code comes from Pagewright, the open template, and every example runs against Toolshop.

## Inside DynamicPage

`DynamicPage` is a class of about 140 lines, and it does three things: it loads a page config and navigates to it, runs actions on the config's fields, and returns locators for assertions. It holds one active config at a time, and each test gets its own instance through the fixture.

A few small decisions are worth noticing:

1. **The config is rebuilt on every call.** `configFactory(this.page)` creates fresh locators against the test's own page. There's no page cache and no state shared between tests.
2. **`onPageInit` runs once per DynamicPage**, which means once per test, on the first `goto`. It's where a client does one-time browser setup, for example a route that blocks an analytics script.
3. **`skipNavigation` switches the config without navigating.** After a click that changes the page, the test tells the engine where it is instead of jumping to a URL, so the transition itself gets tested.
4. **`domcontentloaded`, not `networkidle`.** Navigation waits only until the HTML has loaded. Whether the page is ready is checked through the elements the test actually needs, which is why the ESLint rule from the first article bans `networkidle` in tests. In an app with polling or websockets, the network simply never goes quiet.
5. **Retry on navigation only.** Three attempts, waiting 1 and then 2 seconds between them. Loading the same URL twice is safe, so a momentary network failure doesn't fail a test. A click isn't safe to repeat: a second click on Submit can create a second order, and a click that failed usually points to a real problem. So field actions are not wrapped in retry.

The important line is the `throw`. Without it, a missing value would become `/product/undefined`, the browser would show an error page, and the test would fail three steps later on an element it couldn't find. This way it fails where the problem is, with the placeholder's name in the message.

### getLocator and assertions

`executeSection` is for actions. For checks, the test asks for a locator by section and field name and passes it to Playwright's `expect`, or to a thin helper such as `assertElementHasText`. A missing field fails with the same message as in `executeSection` (`Field "x" not found in section "y"`), and calling it before `goto` fails clearly too: `No page configuration loaded. Call goto() first.`

## The action map: from a name to a function

Every action in the system is a function with the same signature: a locator and an optional value.

<RepoCode file="core/page/types.ts" lines="6" match="export type ActionFunction" matchLine="6" />

That single signature is what lets the engine run any action the same way, without knowing what it does. The trade-off is that the value is typed as `unknown`, so each action has to interpret it itself, and that's where it can quietly go wrong. Test data often arrives as strings, and `Boolean('false')` is `true`. So `check` and `toggle` accept only a real `true` or `false` and fail on anything else, including a missing value.

The `DynamicPage` constructor builds the map from two sources:

<RepoCode file="core/page/DynamicPage.ts" lines="34-53" match="const builtIn: Record<string, ActionFunction>" matchLine="34" />

The built-in actions, and what each does with its value:

| Action | What it does | Value |
| --- | --- | --- |
| `fill` | Fills a field and confirms the value landed | The text |
| `click` | Clicks | Not used |
| `check` | Checks or unchecks a checkbox | `true` / `false` |
| `radio` | Selects a radio button, by label if given | The label, optional |
| `toggle` | Moves a switch to a given state, only if it isn't there already | The target state |
| `selectOption` | Selects an option in a native `<select>` | A value or a list |
| `upload` | Uploads files, after checking they exist | A path or a list of paths |
| `waitForElement` | Waits for the element to be visible | Timeout in ms, optional |
| `getText` | Reads text, and stores it in `SharedData` if given a key | The key, optional |

`getText` closes a loop with placeholders. A field with `{ action: 'getText', value: 'orderId' }` reads an order number from the page and stores it, and a page whose URL is `/orders/${orderId}` later opens with that value. Information moves between steps without the test holding variables.

### Three ways to add an action

1. **`ClientDefinition.actions`**: actions for a whole application. Because of the spread order, a client action with the same name as a built-in one replaces it. An app where every `click` needs a scroll first gets its own `click`, and all the page configs stay as they are.
2. **`registerAction`**: an action registered at runtime, on one test's DynamicPage. Useful for rare cases, like a test that needs special behavior for one field.
3. **Packs**: a set of actions for a specific UI library that a client opts into explicitly. Pagewright ships with a pack for MUI:

```ts
import { muiActions } from '@core/actions/packs/mui';

const client: ClientDefinition = {
  // ...
  actions: { ...muiActions },
};
```

Why a pack? Because the core shouldn't assume which UI library an application uses. `muiAutocomplete` is broken anywhere there's no MUI, so it comes in only when a client asks for it.

## The actions layer: deliberately thin wrappers

Behind the map are four classes: `ElementActions`, `InputActions`, `WaitAndAssertActions` and `FileUploadActions`. They do very little, and that's on purpose:

<RepoCode file="core/actions/ElementActions.ts" lines="7-10" match="async click(locator: Locator)" matchLine="7" />

There's no `waitFor`, no visibility check and no retry. Playwright's `locator.click()` already waits for the element to be visible, stable, enabled and able to receive events. A wrapper that adds its own `waitFor` only doubles the wait, and a wrapper with retry hides real bugs. The rule for this layer: add only what Playwright doesn't give you.

What the wrappers do add:

| Class | What it adds on top of Playwright |
| --- | --- |
| `InputActions` | After `fill`, confirms with `toHaveValue` that the value stayed in the field. Fields with a mask or automatic formatting sometimes change what was typed, and the failure should happen here, not when the form is submitted. |
| `ElementActions` | A log line for every action, and a `toggle` that clicks only if the switch isn't already in the requested state. Two runs of the same test end in the same state. |
| `FileUploadActions` | Checks that every file exists before uploading, and fails with `Upload file not found` and the missing paths instead of a generic error from `setInputFiles`. |
| `WaitAndAssertActions` | An `isVisible` that returns `true` or `false` instead of throwing, for flows where an element only sometimes appears, like a cookie banner. |

The real gain of the layer is that it's one place. When it turns out that every amount field in the app is reformatted while typing, you fix one action and every test gets the fix. And when an action lies, every test lies together. That's exactly what happened in the next case.

## Case study: an autocomplete that reported a success that never happened

In the original framework, MUI autocomplete fields were the least stable part of the forms. The list loads from the server, filters as you type, and closes when the field loses focus. So their action ran inside a retry loop, and before selecting an option it checked whether the value was already in the field, to save unnecessary work.

### The symptom

A test filling a form passed the autocomplete step without an error, and failed only on submit, with a validation error about an empty field. The log showed that the action had reported success: the value was already selected. When a test fails three steps after the place where the problem started, the whole investigation starts in the wrong place.

### The mechanism

In an autocomplete, the text in the input is not the field's value. When you type `USD` to filter the list, the input contains `USD` even if no option was selected. Here's what happened, simplified:

1. The first attempt typed `USD`, the list hadn't finished loading, and the option wasn't found. The action threw an error, but the typed text stayed in the field.
2. The next attempt started with the check "is the value already there?", read the input, found `USD`, and returned success.
3. When the field lost focus, MUI cleared the unselected text, and the form was submitted with an empty field.

The immediate fix was to clear the field before throwing, so a failed attempt leaves nothing behind. But the deeper lesson is that the check itself was wrong: it checked the text the action itself had typed, not the state the application had saved.

### The same pattern in Pagewright

When I went back to the code while writing this article, I found the same pattern in the template's MUI pack:

```ts title="core/actions/packs/mui.ts (before the fix)"
async function pickOption(input: Locator, option: string): Promise<void> {
  await input.click();
  await input.fill(option);
  await input.page().getByRole('option', { name: option, exact: true }).click();
}

export const muiActions: Record<string, ActionFunction> = {
  muiAutocomplete: async (locator, value) => {
    await pickOption(locator, String(value));
    await expect(locator).toHaveValue(String(value));
  },
  muiMultiAutocomplete: async (locator, value) => {
    for (const option of value as string[]) {
      await pickOption(locator, option);
    }
  },
};
```

The `toHaveValue` looks like verification, but it always passes: two lines earlier, the action itself typed exactly that value. And the multi version has no check at all.

The fix checks what the application saved:

<RepoCode file="core/actions/packs/mui.ts" lines="10-26" match="await locator.blur();" matchLine="15" />

The `blur` is the key. In MUI's default mode, unselected text is cleared when the field loses focus, so afterwards the value survives only if an option was really selected. In `freeSolo` fields, which accept free text, blur clears nothing, so this check can't tell a selection from typing. The pack isn't meant for them: there the typed text really is the value, and a plain `fill` is enough. Pagewright's tests for the pack run against real MUI components, including one that rejects the selection, to prove the action now fails when it should.

The rule that carries over to every action in the system: **an assertion that checks something your own action just did proves nothing.** A good check asks a question only the application can answer: a chip that was created, a value that survived blur, or a response from the server. The same principle is behind the check in `fill`: it's worth something only because masked fields change what was typed.

## Action or helper?

A new action is worth it when it describes an interaction with **one element** that repeats across many pages: an autocomplete, a date picker, a masked field. It goes into the map once, and any field in any config can use it by name.

A process that spans several sections or several pages, like a full purchase or a multi-step approval, doesn't belong in the action map. It belongs in a helper that uses `DynamicPage` and calls `goto` and `executeSection` like a regular test. When an action starts navigating between pages or calling an API, that's a sign it's in the wrong place. The original framework's helper layer gets its place in the last article of the series.
